# Курсовая работа по распределенным системам обработки информации

В ходе выполнения данной работы был разработан прототип онлайн-сервиса бронирования отелей.
## Структура системы
Система имеет микросервисную архитектуру и состоит из следующих микросервисов:
1. *Frontend*. Отвечает за предоставление пользователям интерфейса для взаимодействия с системой.
2. *Gateway*. Отвечает за прием запросов от *Frontend* и распределение задач между другими микросервисами. Полное описание запросов, обрабатываемыми *Gateway* представлено в [API Gateway](https://github.com/CALLlA-74/hotel-booking-system-python-realise/blob/main/v2/%5Binst%5D%5Bv2%5D%20Hotels%20Booking%20System.yml).
3. *Identity Provider*. Отвечает за регистрацию/авторизацию пользователей. Для хранения данных пользовательских аккаунтов используется СУБД Postgre SQL. В качестве ответа при успешной **регистрации/авторизации** пользователь получает пару токенов: *ACCESS* и *REFRESH*, защищенных цифровой подписью с помощью алгоритма RS256. *Access*-токен отправляется в заголовках всех остальных запросов к системе для подтверждения своих прав доступа для запрашиваемой операции. Валидация токена осуществляется путем проверки его подписи: каждый из сервисов запрашивает у *Identity Provider* список публичных JWK и по kid токена находит ключ для проверки подписи.
  После экспирации *Access*-токена новая пара токенов может быть получена с помощью токена *Refresh* (если период его экспирации еще не прошел; иначе пользователь будет перенаправлен на страницу авторизации). Периоды экспирации токенов настраиваются в конфигурации сервиса *Identity Provider*.
5. *Loyalty Service*. Отвечает за обработку данных клиентов (количество бронирований, размер скидки, статус в рограмме лояльности) в программе лояльности. Данные хранятся в СУБД Postgre SQL.
6. *Reservation Service*. Отвечает за обработку информации, связанную с отелями и бронированием номеров. 
7. *Payment Service*. Отвечает за обработку информации об оплате. Хранение данных об оплате осуществляется в СУБД Postgre SQL.
8. *Statistic Service*. Отвечает за сбор и обработку данных об операциях пользователей системы. Для сбора информации используется система обмена сообщениями Apache Kafka. Для хранения данных статистики используется СУБД Postgre SQL.

## Руководство по развертыванию

### Локальное развертывание
Для локального развертывания на устройстве необходимо иметь установленный [docker compose](https://docs.docker.com/compose/install/standalone/). 
* Далее запустить сборку образов: `docker compose build`
* Затем поднять контейнеры: `docker compose up -d`

### Развертывание в Kubernetes
В ходе выполнения работы разработанный прототип развертывался в кластере Kubernetes, арендованном в PaaS Yandex Cloud.
Перед тем, как приступить к загрузке и развертыванию сервиса необходимо:
1. зарегистрироваться в [Yandex Cloud](https://center.yandex.cloud).
2. проверить привязку платежного аккаунта, платежной карты к нему.

Для возможности загрузки и дальнейшего развертывания выполняем следующее:
1. В каталоге сервисов выбираем и создаем Managed Service for Kubernetes ([см. инструкцию здесь](https://yandex.cloud/ru/docs/managed-kubernetes/quickstart?from=int-console-empty-state#add-conf)).
2. Создаем статический файл конфигурации для удаленного доступа к кластеру (см. [инструкцию](https://yandex.cloud/ru/docs/managed-kubernetes/operations/connect/create-static-conf)). Далее содержимое полученного файла помещаем в GitHub Secrets с именем KUBECONFIG_FILE, а сертификат подписи помещаем в GitHub Secrets KUBECONFIG_CA_FILE. Данные "секреты" будут использоваться при деплое.
3. Перед непосредственной загрузкой в кластер будут собраны образу микросервисов и помещены в Container Registry, откуда они уже будут загружаться в кластер Kubernetes. Создаем сервисные аккаунты для доступа к Container Registry ([инструкция](https://yandex.cloud/ru/docs/managed-kubernetes/tutorials/container-registry)) и создаем "секрет" CRYANDEX_PASSWORD, куда помещаем пароль от Container Registry.
4. Для предоставления доступа извне к микросервисам, которые будут развернуты внутри кластера, и маршрутизации трафика к ним устанавливаем Ingress-контроллер NGINX (см. [инструкцию](https://yandex.cloud/ru/docs/managed-kubernetes/tutorials/ingress-cert-manager#install-controller)). Затем с помощью команды `kubectl get svc` необходимо убедиться, что Ingress-контроллер установлен успешно и ему выдан External-IP.

Далее запускаем pipeline на загрузку и развертывание в GitHub Actions, описанного в [./.github/workflows/classroom.yml](https://github.com/CALLlA-74/hotel-booking-system-python-realise/blob/main/.github/workflows/classroom.yml).

## Руководство по использованию
При локальном развертывании для доступа к системе переходим по URL:  [http://localhost:3000](http://localhost:3000).

При развертывании в Kubernetes для доступа к системе переходим по следующему URL: `http://[внешний адрес Load Balancer]`

Далее появится форма авторизации: для доступа к пользовательскому функционалу системы необходимо авторизоваться по имени пользователя и паролю, либо зарегистрироваться (если не были зарегистрированы ранее), перейдя на страницу регистрации.

После регистрации/авторизации пользователь перенаправляется на страницу выбора отелей: можно выбрать отель и кликнуть "забронировать" -- во всплывающем окне выбрать даты бронирования и подтвердить действие. Информация о бронировании появится в профиле клиента.

Навигация между разделами сервиса осуществляется по ссылкам в хэдере веб-страницы: можно перейти в профиль пользователя, где размещена информация о статусе клиента в программе лояльности и данные по его бронированиям; или перейти на страницу выбора отелей.

В панели администратора в хэдере страницы также доступен раздел статистики, где выводится информация о действиях пользователей в системе, а также среднее время обработки запросов каждым из микросервисов. Для доступа к панели администратора надо авторизоваться:
* имя пользователя: admin
* пароль: admin
